## Conclusion

MVVM gave us a presentation layer that we can test completely without JavaFX: validation messages, command enablement, progress, failure, cancellation and the product filter are all checked in milliseconds with a fake source and `ManualJobs`, which was impossible with the MVC controller because it reads and writes controls directly. The same separation made the background load easy to add, because the worker only receives a snapshot of the inputs and the ViewModel properties are written back on the UI thread; load time stayed about the same (283 ms against 290 ms) while the worst frame gap fell from 339 ms to 22 ms. What got worse is size and indirection: we went from one 41-line controller to a 244-line ViewModel plus ports, commands and job classes, and a wrong binding fails silently in the view instead of at a line we can step through. A bug such as the concatenated top-products list is also less obvious, because the data passes through several observable layers before it appears. We would still choose MVC for a throw-away screen or a tool with one form and no rules, where the extra classes cost more than the tests save. For a screen with validation, long-running loads and a possible second view (the dashboard challenge), MVVM pays for itself.
